# NetSentry v3.1.0 — Native nftables and IDS Validation

**Release Date:** 2026-08-27  
**Status:** Stable  
**Type:** Firewall, networking, and security validation milestone

---

## Release Summary

NetSentry v3.1.0 completes the migration of the gateway firewall from the retired NetSentry iptables implementation to native nftables. It also adds repeatable Suricata PCAP validation and updates the project documentation to match the active Linux networking, IDS, SIEM, and service architecture.

This release keeps the project focused on practical telecom and networking fundamentals, Linux gateway administration, SOC visibility, and defensive cybersecurity operations.

---

## Major Changes

### Native nftables Firewall

NetSentry now owns a native nftables ruleset in:

```text
table inet netsentry
```

The active chains are:

| Chain | Purpose |
| --- | --- |
| `input` | Default-drop protection for the gateway host |
| `forward` | Controlled forwarding between home, AP, and internet paths |
| `postrouting` | AP-to-internet masquerading while preserving AP source addresses toward the home LAN |

The rules include connection tracking, loopback and ICMP handling, DNS and DHCP access for AP clients, administrative access controls, Tailscale management access, forwarding policy, NAT, and rate-limited drop logging.

The previous `scripts/apply_firewall.sh` and `netsentry-firewall.service` files are retained only as historical references. They are not the active firewall deployment path.

### Ansible Deployment and Persistence

The firewall deployment pipeline is now:

```text
config/vars.yml
    -> templates/firewall.nft.j2
    -> playbooks/firewall.yml
    -> /etc/nftables.conf
    -> nftables.service
```

The Ansible playbook:

- Installs nftables
- Persists `net.ipv4.ip_forward=1`
- Renders the Jinja nftables template
- Validates the rendered configuration with `nft --check`
- Installs `/etc/nftables.conf`
- Enables and starts `nftables.service`
- Reloads the service when the template changes

Deployment command:

```bash
ansible-playbook playbooks/firewall.yml --ask-become-pass
```

### Suricata PCAP Validation

The repository now includes repeatable offline validation for versioned Suricata rules:

```text
tests/cases/<SID>/<SID>.pcap
```

Run every test case or one selected SID:

```bash
python3 tests/cases/validate.py
python3 tests/cases/validate.py 10000001
```

For each case, the validator:

1. Runs Suricata against the fixture in a fresh temporary log directory.
2. Parses newline-delimited EVE JSON output.
3. Confirms that the expected directory SID triggered.
4. Fails if any different SID triggered.
5. Removes temporary output after validation.

Exit codes:

| Code | Meaning |
| ---: | --- |
| `0` | Every selected case passed |
| `1` | One or more alert-validation failures |
| `2` | Configuration, discovery, execution, or missing-output error |

### PCAP Inspection Utility

`tests/cases/run_pcaps.py` runs the fixtures through `tcpdump` for capture inspection and readability checks:

```bash
python3 tests/cases/run_pcaps.py
python3 tests/cases/run_pcaps.py 10000001
```

This utility does not validate Suricata alerts. `validate.py` remains the correctness test.

## Security and Operational Notes

### Full-ruleset Flush

The nftables template currently begins with:

```nft
flush ruleset
```

This removes all nftables tables, including compatibility rules owned by Tailscale and possible rules owned by containers or other firewall managers. Restart Tailscale after firewall deployment:

```bash
sudo systemctl restart tailscaled
```

### AP-to-home Trust Boundary

The current forwarding policy allows AP clients to initiate connections to the full home subnet. This is not an isolated guest-network policy. Restrict the rule to explicit destinations and ports if broad access is not intended.

### Deployment-specific Test Paths

The Suricata validation scripts currently use these paths:

```text
/home/gbx/netsentry-gateway/suricata/rules/local.rules
/etc/suricata/suricata.yaml
```

Update the script constants if the checkout or deployed Suricata configuration is located elsewhere.

## Validation Checklist

### Firewall and Forwarding

```bash
sudo systemctl is-enabled nftables
sudo systemctl status nftables --no-pager
sudo nft list table inet netsentry
sudo sysctl net.ipv4.ip_forward
```

Expected results:

- `nftables.service` is enabled and active.
- `table inet netsentry` contains the input, forward, and postrouting chains.
- Input and forwarding use default-drop policies.
- IPv4 forwarding is set to `1`.

### Tailscale Coexistence

```bash
sudo systemctl restart tailscaled
sudo iptables-save
sudo ip6tables-save
```

Any `ts-*` chains are owned by Tailscale through the iptables-nft compatibility backend. Retired NetSentry iptables chains must not be present.

### IDS Validation

```bash
sudo suricata -T \
  -c /etc/suricata/suricata.yaml \
  -S /home/gbx/netsentry-gateway/suricata/rules/local.rules \
  -i wlx200db0220b9a \
  -l /tmp/suricata-rule-test

python3 tests/cases/validate.py
```

### SIEM Pipeline

Confirm that:

- Suricata writes alerts to `/var/log/suricata/eve.json`.
- Filebeat ships events to Wazuh.
- Wazuh receives Suricata and nftables events.
- Firewall log prefixes are searchable in kernel logs and Wazuh.

### Network Behavior

Confirm that:

- AP clients receive DHCP leases.
- AP clients use the gateway DNS service.
- DNS filtering works through AdGuard Home.
- AP-to-internet forwarding and masquerading work.
- Return traffic reaches AP clients.
- Home/AP traffic follows the intended trust boundary.
- Services and routing recover correctly after reboot.
